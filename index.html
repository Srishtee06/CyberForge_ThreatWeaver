Why ThreatWeaver vs. EDR & Traditional SIEM

            
Technical differentiation across 4 core architectural dimensions

          

        

        
      


      

        
        

          
          

            

              1
              
Cross-Domain Visibility vs. Endpoint Blind Spots

            

            

              The Problem: Traditional EDRs (CrowdStrike, Defender for Endpoint) require kernel sensor
              agents. They have absolute blind spots on perimeter appliances (VPN-GW-01), unmanaged switches, and external cloud
              firewalls.

              ThreatWeaver: Ingests agentless network, firewall, VPN, Active Directory, and host
              telemetry simultaneously to stitch complete cross-domain pivots: VPN-GW-01 ➔ DEV-JUMP-01 ➔ K8S-CTRL-01.
            

          


          
          

            

              2
              
Alert Compression & Graph Provenance vs. Alert Fatigue
              

            

            

              The Problem: Traditional SIEMs (Splunk, Microsoft Sentinel) fire thousands of unlinked
              per-rule alerts, causing severe analyst burnout (the landmark 2013 Target breach failure).

              ThreatWeaver: Sliding-window run-length compression and NetworkX provenance graphs
              condense 108,000+ raw log lines into 5 deterministic multi-host kill chains with a
              verified < 4% false alarm rate.
            

          


          
          

            

              3
              
Predictive Look-Ahead Reachability vs. Reactive Detection

            

            

              The Problem: EDRs are purely reactive—they only notify you after malicious
              execution has already taken place on a host.

              ThreatWeaver: Evaluates compromised accounts (adm_backup) against AD privilege ACLs and subnet
              routability (computeLookAhead) to predict which uncompromised
              servers (DC-01, BACKUP-VAULT, ERP-SQL) the attacker can reach
              next, computing dollar-value financial liability ($6.5M) before the pivot occurs.
            

          


          
          

            

              4
              
Zero-Infra Out-of-Core Portability vs. Costly Clusters

            

            

              The Problem: SIEMs require 30-node Elasticsearch / cloud clusters costing thousands of
              dollars per month to ingest a 50GB cold log dump.

              ThreatWeaver: Runs bounded out-of-core streaming on a single standard 16GB
                analyst laptop in < 3.5GB peak RAM via DuckDB disk-spilling and Polars lazy
              pushdown, or via instant zero-install browser mode.

The 5 Explicit Processing Stages


          

            1
            

              Stage 1: Malformed & Null Byte
                Sanitization
              
Strips null bytes (), invalid UTF-8 sequences, and comment
                headers (#) in streaming 4MB/64MB chunks without loading whole files into RAM.

            

          


          

            2
            

              Stage 2: Multi-Schema Canonical
                Normalization
              
Normalizes heterogeneous formats (Key-Value, JSONL, CSV,
                Syslog, Windows Events) into a unified 9-column canonical schema (timestamp, src_ip, dst_ip, src_host, dst_host, user, action, bytes_out,
                  raw_count) with ISO-8601 timestamps and IP fallback.

            

          


          

            3
            

              Stage 3: Early Pushdown Pre-Filtering
              
Filters out 99.9% benign noise (routine HTTP 200 GETs,
                internal ping health checks, single isolated auth typos) before graph construction.

            

          


          

            4
            

              Stage 4: Run-Length Event Deduplication
              
Compresses consecutive identical (src_host, dst_host, user,
                action) events within sliding time windows into high-fidelity attack steps, accumulating raw_count and
                bytes_out.

            

          


          

            5
            

              Stage 5: Tier-Specific Out-of-Core
                Execution
              
Executes query plan across tiers: Polars Lazy Streaming
                (15GB), Parallel Zstd Parquet Partitioning (30GB), or DuckDB Out-of-Core Relational Disk Spilling with
                PRAGMA memory_limit='6GB' (50GB).
